# 폰에서 받아쓰기 — 모델 조사 (2026-09-18)

## 왜 보나

통화 1건 원가 105원 중 **90원(85%)이 받아쓰기**다. 공급자를 바꿔서는 한 푼도 못 아낀다는
것이 이미 확인됐으므로(→ `jayeon-was/docs/llms.md`), 줄이는 길은 **받아쓰기를 폰에서
하는 것** 하나뿐이다. 그러면 서버는 분석만 하므로 **105원 → 13원**이 된다.

품질이 되는지는 이미 확인했다(→ `jayeon-was/docs/asr-comparison.md`): 맥북에서 돌린
`large-v3-turbo` 가 알리바바와 대등했다. 이 문서는 **그 품질을 폰에 넣을 수 있는 크기·속도로
낼 수 있는가**를 조사한 기록이다.

🔴 **전제가 바뀌었다는 것을 먼저 알아야 한다.** 예전에 폰 받아쓰기를 접었을 때는 787MB 안에
**받아쓰기 모델과 요약 모델을 둘 다** 넣어야 했다. 지금은 요약을 서버가 하므로 **그 용량
전부를 받아쓰기에 줄 수 있다.** 그때의 실패를 근거로 이 선택지를 버리면 안 된다.

## 1. 🔴 결정적 근거 — 한국어 「전화 통화」 벤치마크

**OpenKoASR 리더보드**, AIHub **저품질 전화망**(LowQualityTelephone) 39,916 샘플 전수.
낭독체가 아니라 **우리 조건과 같은** 데이터다.

| 모델 | CER | WER | 크기(f16) |
|---|---|---|---|
| whisper **large-v3** | **0.1062** | 0.2837 | 2.9GB |
| whisper **large-v3-turbo** | **0.1087** | 0.2882 | 1.5GB |
| qwen3-asr-1.7b | 0.1993 | 0.4445 | ~3.4GB |
| qwen3-asr-0.6b | 0.2437 | 0.5212 | ~1.2GB |
| whisper medium | 0.3017 | 0.5637 | 1.5GB |
| whisper **small** ← 예전 폰이 쓰던 급 | **0.3358** | 0.6126 | 466MB |
| whisper base | 0.4344 | 0.7466 | 142MB |
| whisper tiny | 0.5404 | 0.8429 | 75MB |

출처: https://gt-kim.github.io/open-korean-automatic-speech-recognition/leaderboard.md (2026-09-18 확인)

**읽는 법 셋:**

1. **turbo 는 large-v3 대비 오류가 2.4%만 늘어난다.** 크기는 절반인데. 맥북 실측(9,863자 vs
   알리바바 9,976자)과 정확히 맞아떨어진다.
2. 🔴 **small → turbo 는 CER 0.336 → 0.109, 오류가 3분의 1이다.** 「더메이」가 「도매」가 되고
   「아저씨」가 「저시」가 된 이유가 여기 있다. **체급 문제라 프롬프트로 메울 수 있는 수준이
   아니었다.**
3. 🔴 **중간 선택지가 없다.** medium(0.3017)부터 이미 무너진다. 「적당히 작은 모델로 타협」이라는
   길은 이 데이터에 존재하지 않는다 — large 계열이거나 포기거나 둘 중 하나다.

⚠️ **Qwen3-ASR 오픈소스판(0.6B/1.7B)은 이 조건에서 Whisper 보다 크게 나쁘다**(0.2437 / 0.1993).
서버에서 쓰는 알리바바 `qwen-audio-3.0-asr-flash` 와 **이름만 비슷할 뿐 다른 물건이다.**
낭독체(Fleurs-ko CER 3.72%)에서는 좋아 보이는데 전화 음성에서 무너진다 — **낭독체 점수에
속으면 안 되는 대표 사례다.**

## 2. 한국어 파인튜닝 모델 — 권하지 않는다

실재를 확인한 것(2026-09-18, HuggingFace API 로 파일 실물 확인):

| 저장소 | 내용 | 점수 | 주의 |
|---|---|---|---|
| `royshilkrot/whisper-large-v3-turbo-korean-ggml` | zeroth-korean + STT_Korean_Dataset_80000, ~102k 문장 | WER 24 → 16 | Apache-2.0. 평가셋 불명시 |
| `JoaoZaokk/whisper-large-v3-turbo-korean-ggml` | 위 모델의 GGML 변환판. f16 1,625MB / q8_0 874MB / q5_0 574MB / q4_0 474MB | 자체 측정 없음 | **2026-09-12 생성, 다운로드 0회 — 전혀 검증 안 됨** |
| `ghost613/whisper-large-v3-turbo-korean` | zeroth-korean 206시간 | val CER 1.78% | zeroth **자체 test셋** 점수. 작성자가 "수렴 안 됨" 명시 |

🔴 **셋 다 학습·평가가 전부 `zeroth-korean`(낭독체 고음질)이다.** CER 1.78% 는 「낭독체를
낭독체로 평가」한 숫자라 전화 통화에 적용되지 않는다. 오히려 **낭독체 단일 도메인에
과적합되어 전화 대화체에서 원본보다 나빠질 위험**이 실재한다.

전화·대화체로 파인튜닝된 공개 한국어 Whisper 는 **찾지 못했다.**

→ **원본 turbo 로 먼저 가고**, 파인튜닝판은 같은 통화로 A/B 해 본 뒤에만 고려한다.

## 3. 속도 — 예상보다 낙관적이다

whisper.rn 이 **2026-09-17(조사 하루 전)** 갤럭시 Hexagon NPU 백엔드를 머지했다(PR #337).
그 PR 본문의 **Galaxy S25 Ultra** 실측(30초 청크 1회, ms):

| 모델 | 인코더 | 디코더(토큰당) |
|---|---|---|
| small-q8_0 | 164.13 | 7.24 |
| medium-q8_0 | 372.72 | 21.90 |
| **large-v3-turbo** | **1010.32** | 7.46 |
| **large-v3-turbo-q8_0** | **946.34** | 7.12 |

> PR 원문 주석: **"q5_0 / q5_1 are not supported in ggml-hexagon (will fallback to cpu)"**

출처: https://github.com/mybigday/whisper.rn/pull/337 (2026-09-18 확인)

28분 26초(1,706초) 러프 추정: 30초 청크 57개 × 946ms ≈ 인코더 54초, 디코더 6,000~8,000토큰
× 7.12ms ≈ 43~57초 → **합계 1분 40초 ~ 2분.**

⚠️ **이 추정을 믿지 마라.** mel 추출·temperature 재시도·VAD·파일 I/O 가 빠져 있고, 발열
스로틀링도 미반영이다. 표의 `Config` 열이 전부 `NEON` 이라 **이 수치가 NPU 경로인지 CPU
경로인지 PR 본문만으로는 단정할 수 없다.** **현실적 기대치는 2~5분**으로 잡고 실측한다.

### 🔴 예전 폰 실패를 다시 해석해야 한다

이 조사 중에 잰 「whisper.cpp `small`, **CPU 1스레드**, 120초 오디오 → 149초」(실시간보다 느림)는
위 표의 small 인코더 165.76ms/30초청크와 **수십 배** 차이가 난다. 즉 그 측정은 **설정이 나쁜
조건**이었고, 예전 폰 받아쓰기 실패도 모델 크기뿐 아니라 **스레드·백엔드 설정 문제였을
가능성이 있다.** 이것도 재측정 대상이다.

## 4. 🔴 고유명사 프롬프트 — 함정이 있다

기준선 실패가 전부 고유명사였다. 회사명 「더메이」와 상담사 이름은 **매번 나오는 고정값**이라
미리 알려 줄 수 있다.

**whisper.cpp 는 hotword/biasing API 가 없다.** 전용 API 요청(issue #1979)은 *closed as not
planned* 로 닫혔다. 쓸 수 있는 것은 셋뿐이다:

1. `--prompt` (initial prompt) — 지원됨
2. `--grammar` (GBNF) + `--grammar-penalty` — 자유 발화 전사엔 부적합
3. 모델 밖 후처리 교정 테이블 — 「도매」→「더메이」 치환

### 함정: 28분 통화에서 프롬프트는 첫 30초에만 걸린다

whisper.cpp 소스 확인 결과, `carry_initial_prompt` 가 `false`(기본값)면 initial prompt 가
롤링 컨텍스트에 밀려 **이후 창에서 사라진다.** `true` 여야 모든 30초 창에 계속 주입된다.

🔴 **그런데 whisper.rn 의 `TranscribeOptions` 에 `carryInitialPrompt` 가 없다.** 노출된 것은
`prompt`, `beamSize`, `bestOf`, `maxContext`, `temperature`, `maxThreads`, `maxLen`,
`tokenTimestamps`, `tdrzEnable` 등이다.

**우회책 둘** (측정해서 고른다):
- **(a)** JS 에서 오디오를 청크로 잘라 각각 transcribe 하며 **매번 같은 prompt 전달.** 코드 수정
  없이 가능. 청크 경계에서 문장이 끊기므로 경계를 무음 지점으로 잡으면 완화된다.
- **(b)** whisper.rn 에 `carryInitialPrompt` 옵션 추가 패치. 네이티브 한 줄 + 타입 한 줄 수준.
  업스트림 PR 가치가 있다.

### ⚠️ 프롬프트의 부작용

initial prompt 는 「부드러운 힌트」가 아니라 **강한 의미적 제약**으로 작동해, 오디오에 없는
표현을 넣는 **환각과 반복 루프**를 유발한다. **일본어·한국어에서 반복 환각 보고가 특히 많다.**
프롬프트가 문어체면 「어…」 같은 간투사를 생략하는 경향도 있어 **구어체로 쓰는 편**이 낫다.
권장 길이는 20~100 토큰의 고관련 어휘.

→ 프롬프트 **있음/없음 두 버전을 같은 통화로 비교한 뒤** 채택한다. 회사명 목록이 확정적이면
후처리 교정 테이블을 병행하는 편이 안전하다.

## 5. 화자 분리 — 35MB 로 해결된다

**이 발견으로 「타협 불가」 전제가 풀린다.** 원래 화자 분리 때문에 Groq(68% 저렴)을 탈락시켰고
서버 ASR 을 못 바꾼다고 판단했는데, 폰에서 붙일 수 있다.

**sherpa-onnx**(k2-fsa) 오프라인 화자분리. 세그멘테이션 + 임베딩 2단:

| 역할 | 모델 | 크기 |
|---|---|---|
| 화자 세그멘테이션 | `sherpa-onnx-pyannote-segmentation-3-0` | **6.6MB** |
| 화자 임베딩 | `3dspeaker_speech_campplus_sv_zh_en_16k` | **27.0MB** |

- **언어 무관** — 음향 특징 기반이라 한국어와 상관없다
- 안드로이드 공식 지원(전용 APK 배포 중), React Native 바인딩 `react-native-sherpa-onnx`
  v0.4.4 (MIT, 2026-09-08) 존재. ⚠️ 서드파티라 검증은 직접 해야 한다
- ⚠️ Whisper 세그먼트 타임스탬프와 sherpa 화자 구간을 **병합하는 로직은 직접 짜야 한다**
  (공개 RN 레퍼런스 없음)

❌ **whisper.cpp tinydiarize(`-tdrz`)는 쓰지 마라.** whisper.rn 에 `tdrzEnable` 이 있지만
**`small.en` 영어 전용 모델**이 필요하고, 「화자가 바뀜」만 표시할 뿐 **같은 사람을 파일
전체에서 묶지 못한다.**

참고: 이번 비교에서 **화자 분리 없이도 LLM 이 대화 흐름으로 상담원과 고객을 갈라 요약했다.**
즉 화자 분리는 **있으면 좋은 것**이지 필수가 아닐 수 있다(→ `asr-comparison.md`).

## 6. 추천안 (조사 시점 — ⚠️ 7절 실측으로 일부 뒤집혔다)

🔴 **이 절은 실측 전에 쓴 것이다.** 7절에서 맥북으로 직접 재 본 결과 **q5_0(547MB)으로
충분하고 고유명사 프롬프트는 효과가 없다**는 것이 확인됐다. 아래를 그대로 따르기 전에
**7절을 먼저 읽을 것.** 이 절을 남겨 두는 이유는 조사 근거(벤치마크·라이선스·크기)가
여전히 유효하고, 무엇을 왜 그렇게 예상했는지가 다음 판단에 쓰이기 때문이다.

### 1순위 — `large-v3-turbo` **q8_0** (약 874MB) + whisper.rn + Hexagon NPU + 고유명사 프롬프트

| 항목 | 값 |
|---|---|
| 크기 | 약 874MB. 앱 번들이 아니라 **최초 실행 시 다운로드** |
| 한국어 전화 CER | 0.1087 (원본 f16 기준. 양자화 손실은 한국어 미측정) |
| 속도 | **2~5분 추정, 측정 필요** |
| 라이선스 | 모델 MIT / whisper.rn MIT / whisper.cpp MIT — **상업 이용 가능** |
| 화자분리 | 별도 sherpa-onnx +35MB |

🔴 **q5_0(547MB)이 아니라 q8_0 을 고르는 이유**: ggml-hexagon(NPU)이 q5 를 지원하지 않아
**CPU 로 폴백**한다. 속도가 병목이므로 300MB 를 내주고 NPU 를 사는 것이 맞다. NPU 가 실측에서
효과 없으면 그때 q5_0 으로 내려가면 된다.

⚠️ **q4_0(474MB)은 피한다.** 영어 기준으로도 WER +4.9% 가 통계적으로 유의하게 나타나는
지점이다(p=0.001). 「고유명사처럼 저빈도 토큰이 양자화에 먼저 깨진다」고 예상했는데,
**7절 실측에서 q8_0·q5_0 은 고유명사를 하나도 깨뜨리지 않았다** — q4_0 은 측정하지 못했다
(ggerganov/whisper.cpp 저장소에 turbo q4_0 파일이 없다). 양자화 손실 측정
(whisper large-v3, LibriSpeech test-clean): F16 5.35% / Q8_0 5.25% / Q5_0 5.19% / **Q4_0 5.61%**.
출처: https://github.com/yoarajota/whisper-quantization-wer-degradation
⚠️ 이건 **영어 낭독체** 측정이다. 한국어·전화 음성의 양자화 손실은 **확인 불가**.

### 정직한 대가

- **크기**: 앱이 874MB 무거워진다. 오늘 기기 AI 모듈을 걷어내 239MB → 134MB 로 줄인 것을
  상당 부분 되돌리는 셈이다. Play Store 번들 한도 때문에 최초 실행 다운로드가 사실상 유일한 길.
- **속도**: 서버 1분 38초 → 폰 2~5분. 즉시성은 확실히 손해다. 백그라운드 처리 + 완료 알림
  UX 가 필요하다.
- **정확도**: 알리바바와 대등할 가능성이 높지만, **양자화 + 폰 스레드 제약**이 붙은 상태의
  한국어 정확도는 **아무도 측정한 적이 없다.**
- **배터리·발열**: 28분 통화를 수 분간 풀로드. 미측정.

### 2순위 / 3순위

- **2순위**(1순위가 느리면): q5_0 (547MB, CPU 8스레드). NPU 를 포기하고 크기를 줄인다.
- **3순위**(정확도가 부족하면): 한국어 파인튜닝 turbo q8_0. **반드시 같은 통화로 A/B 후** 채택.

## 7. 맥북 실측 결과 (2026-09-18) — ③④는 끝났다

조사 직후 같은 통화(28분 26초)로 **맥북에서 ③④를 실제로 돌렸다.** 둘 다 답이 나왔고,
**아래 6절의 추천안 일부가 이 결과로 바뀐다.**

### ③ 양자화 손실 — 🔴 q5_0(547MB)으로 충분하다

f16 결과를 기준 삼아 CER 을 쟀다(공백·문장부호 제외).

| 모델 | 크기 | CER vs f16 | 전사 시간(M2 Pro, GPU+8스레드) |
|---|---|---|---|
| f16 | 1,549MB | 기준 | 1분 37초 |
| **q8_0** | **834MB** | **3.75%** | 1분 22초 |
| **q5_0** | **547MB** | **4.84%** | 1분 33초 |
| (참고) 폰 소형모델 | ~150MB | **41.64%** | — |
| (참고) 알리바바 | 서버 | 11.49% | — |

🔴 **고유명사는 세 크기에서 완전히 동일했다.** 「양자화는 저빈도 토큰부터 깨진다」는 우려가
이 통화에서는 나타나지 않았다:

| | 더메이 | 도매 | 권자연 | 노블레스 | 노블 | 하이엔드 | 프라우드 | 아저씨 |
|---|---|---|---|---|---|---|---|---|
| f16 | 1 | · | 1 | 2 | 21 | 4 | 1 | 1 |
| **q8_0** | 1 | · | 1 | 2 | 21 | 4 | 1 | 1 |
| **q5_0** | 1 | · | 1 | 2 | 21 | 4 | 1 | 1 |
| 폰 소형모델 | **·** | **1** | 1 | 1 | **3** | **·** | 1 | **·** |

⚠️ 알리바바의 11.49% 는 **틀렸다는 뜻이 아니다.** 서로 다르게 들었다는 것뿐이고, 정답지가
없으므로 이 숫자로 우열을 정할 수 없다. 여기서 f16 을 기준으로 삼은 것은 **양자화 손실만**
분리해서 보기 위해서다.

🔴 **폰 소형모델의 CER 41.64% 가 실패의 크기를 말해 준다.** 특히 「노블」을 21번 중 **3번만**
잡았다 — 경쟁사 비교가 상담의 핵심인데 그 단어를 18번 놓쳤다. 「하이엔드」는 0번이다.
1절 벤치마크(small CER 0.3358)와 방향이 일치한다.

**→ 6절의 「q8_0 을 골라야 한다」는 근거가 약해졌다.** q5_0 이 **300MB 더 작은데 손실은
1%p 차이**다. NPU 가 q5 를 지원하지 않는다는 제약에 매달릴 이유가 줄었다 — 폰에서 q5_0 을
CPU 로 돌린 속도가 감당되면 그쪽이 낫다. **①②를 q5_0 우선으로 측정할 것.**

### ④ 고유명사 프롬프트 — 🔴 효과 없다. 하지 마라

구어체 프롬프트(회사명·경쟁사·프로그램명 포함, 약 80토큰)를 q8_0 에 넣어 같은 통화를 다시 전사했다.

| | CER vs f16 | 더메이 | 노블 | 하이엔드 | 듀오 |
|---|---|---|---|---|---|
| 프롬프트 없음 | **3.75%** | 1 | 21 | 4 | 7 |
| 프롬프트 있음 | **4.04%** | 1 | 21 | 4 | **6** |

**고유명사가 하나도 개선되지 않았고 CER 은 오히려 미세하게 나빠졌다.** 이유는 둘이다:

1. **고칠 것이 없었다.** q8_0 은 프롬프트 없이 이미 전부 맞췄다. 「도매」 문제는 **작은 모델의
   문제였지 프롬프트로 풀 문제가 아니었다.**
2. 4절의 함정이 실증됐다 — 프롬프트는 **첫 30초 창에만** 걸리므로 28분 통화 전체 결과를
   바꾸지 못한다.

**→ 4절이 제기한 `carryInitialPrompt` 패치(우회책 b)와 청크 분할(우회책 a)은 지금 불필요하다.**
모델이 충분히 크면 프롬프트 없이 맞는다. 후처리 교정 테이블도 마찬가지다.

⚠️ 다만 **사람 이름**에는 아직 여지가 있다. 「영현/영연」처럼 인명은 모델마다 갈렸고(맥북·폰은
영현, 알리바바는 영연), 통화 상대는 등록 시점에 **이미 알고 있는 값**이다. 그 한 사람의 이름만
넣는 프롬프트는 회사명과 달리 효과가 있을 수 있다 — **측정한 적 없다.**

### 남은 측정 — 폰이 필요하다

| # | 측정 | 방법 |
|---|---|---|
| ① | **폰 실측 속도** | whisper.rn 의 `bench()` API(`[config, nThreads, encodeMs, decodeMs, batchMs, promptMs]` 반환). **q5_0 을 먼저**, 그 다음 q8_0 × `useGpu` true/false. 가장 싸고 빠른 첫 실험 |
| ② | **28분 전체 처리·발열** | 원본을 16kHz 모노 WAV 로 변환해 실기기 end-to-end 1회. 배터리·스로틀링 포함 |
| ⑤ | **NPU 실효성** | ①에서 `NativeWhisperContext.gpu` / `reasonNoGPU` 확인. 안 잡히면 `libcdsprpc.so` 매니페스트 선언 필요(whisper.rn README). **q5_0 이 충분히 빠르면 이 항목 자체가 불필요해진다** |
| ⑥ | 파인튜닝판 A/B | 맥북에서 먼저 거른다. 우선순위 낮다 — 원본 q5_0 이 이미 고유명사를 다 맞췄다 |
| ⑦ | 화자분리 정확도 | sherpa-onnx 예제를 맥북에서 같은 통화에 돌려 알리바바 0/1 결과와 비교. 폰 통합은 통과 후 |
| ⑧ | **인명 프롬프트** | 통화 상대 이름 하나만 넣어 「영현/영연」이 잡히는지. ④와 달리 아직 미측정 |

### ①②⑤ 를 재는 도구 — 앱의 ☰ 「받아쓰기 시험」

폰에서 재려면 폰에서 돌려야 한다. 그래서 측정 전용 화면을 하나 붙였다(`src/components/asr-bench.tsx`).

🔴 **이 화면은 통화분석 등록 흐름과 이어져 있지 않다.** 속도가 감당 안 되면 폰 받아쓰기는
통째로 버려야 하는데, 먼저 흐름을 갈아 끼우면 되돌릴 것이 많아진다. **측정이 끝나면 이 화면
하나만 지운다** — 재사용할 부분(whisper.rn 설정, 모델 내려받기, 16kHz 변환)은 전부
`src/lib/asr-*.ts` 와 `modules/nature-call-audio` 에 있다.

쓰는 순서:

1. **모델** q5_0 / q8_0 중 고르고 내려받는다. 둘을 동시에 보관할 수 있다(비교해야 하므로).
   APK 에는 들어 있지 않다 — 547MB 를 번들에 넣을 수 없다.
2. **백엔드** NPU/GPU 켬·CPU 만 중 고른다. 모델을 연 뒤 🔴 **`gpu` / `reasonNoGPU` 실측값이
   화면에 뜬다** — 「NPU 를 쓴다고 생각했는데 CPU 였다」가 이 측정의 최악이라 기대가 아니라
   결과를 본다.
3. **벤치**(①) 30초 청크 1회. 몇 초면 끝나니 전체 받아쓰기 **전에** 돌린다.
4. **녹음 고르기** 다운로드 폴더의 `consult-test.m4a`.
5. **전체 받아쓰기**(②) 변환 → 전사. 경과 시간이 실시간으로 뜨고, 진행률은 whisper.cpp 가 준
   값일 때만 그린다. ⚠️ **변환 시간도 따로 잰다** — 받아쓰기만 재면 사용자 대기 시간이 아니다.
6. **결과** 변환/받아쓰기/합계·실시간 대비 배수·글자 수·NPU 여부·스레드 수. 🔴 **원문을
   내보내거나 복사할 수 있다** — 맥북 f16 결과와 CER 을 비교하지 못하면 「돌아갔다」만 알고
   품질은 모른 채로 끝난다.

처리 중에는 화면을 깨워 둔다(`expo-keep-awake`). 28분을 기다리다 화면이 꺼져 측정이 죽으면
28분을 다시 기다려야 한다. ⚠️ 앱이 백그라운드로 가는 것은 막을 수 없어서 **갔다는 사실을
결과에 적는다** — 그 시간은 기기 성능이 아니라 OS 의 CPU 조이기가 만든 숫자다.

**whisper.rn 은 `0.8.0-rc.1` 로 고정했다.** Hexagon NPU(PR #337)가 들어간 첫 배포판이고,
`0.7.4`(정식 최신)에는 없다. 프리릴리스라 캐럿(`^`) 없이 정확한 버전을 박아 뒀다 —
측정 결과가 어느 코드의 숫자인지 흔들리면 안 된다.

⚠️ NPU 를 쓰려면 매니페스트에 `<uses-native-library android:name="libcdsprpc.so" .../>` 가
있어야 하고, 없으면 **조용히 CPU 로 폴백한다**(빌드도 실행도 성공한다). 그 선언은
`plugins/with-whisper.cjs` 가 넣는다.

### 재현 방법

```
# 모델: https://huggingface.co/ggerganov/whisper.cpp/resolve/main/ggml-large-v3-turbo-{q8_0,q5_0}.bin
#   ⚠️ q4_0 은 이 저장소에 없다(2026-09-18 확인).
ffmpeg -i 녹음.m4a -ar 16000 -ac 1 -c:a pcm_s16le consult.wav
whisper-cli -m ggml-large-v3-turbo-q5_0.bin -f consult.wav -l ko -t 8 -of out -oj
# 프롬프트를 넣어 볼 때는 --prompt "..." 를 더한다
```
CER 은 공백·문장부호를 걷어 낸 뒤 편집거리 / 기준 길이로 계산했다.

## 8. 🔴 폰 실측 결과 (2026-09-19) — **온디바이스는 실패다** (⚠️ 10절 아이폰 실측으로 뒤집혔다)

①②⑤를 실제로 재 봤고, **결론은 「지금 있는 기기로는 안 된다」**다.

### 무엇이 막았나 — NPU 가 없다

whisper.rn 의 가속 백엔드는 **ggml-hexagon**, 즉 **퀄컴 스냅드래곤의 Hexagon NPU 전용**이다.
보유 기기가 둘 다 해당하지 않았다:

| 기기 | 칩 | 결과 |
|---|---|---|
| 갤럭시 S21 (SM-G991N) | **Exynos 2100**(삼성) | Hexagon 없음 |
| 갤럭시 A16 (SM-A165N) | **MediaTek MT6789** | Hexagon 없음 |

측정 화면이 그대로 말해 줬다: **「CPU 로 열렸습니다 — Hexagon backend not available in this build」**

🔴 **이 한 줄을 화면에 띄우게 한 것이 이번 측정을 구했다.** 없었다면 28분 통화를 걸어 놓고 몇
시간 뒤에야 「왜 이렇게 느리지」를 의심했을 것이다. 라이브러리도 매니페스트 선언도 APK 자산도
전부 정상이었고, **빌드와 실행은 성공한 채 속도만 무너지는** 실패다.

### CPU 폴백 실측

| 조합 | 30초 오디오 처리 | 28분 통화 환산 |
|---|---|---|
| q5_0 + NPU 켬 → CPU 폴백 (4스레드) | **3분 이상**(CPU 시간 11분) | **약 3시간** |
| q8_0 + NPU 켬 → CPU 폴백 | 같은 양상 | 같음 |

⚠️ 3절에 인용한 **Galaxy S25 Ultra 946ms 는 스냅드래곤 + NPU 수치**였다. 그때 「NPU 경로인지
CPU 경로인지 단정할 수 없다」고 단서를 달았는데, 답은 **NPU 경로**였다. 그 숫자를 엑시노스
기기에 대입한 것이 어긋난 지점이다.

### 작은 모델로 내려갈 길도 없다

1절 표가 그대로 답이다 — CPU 가 감당할 크기(medium 0.3017 / small 0.3358)는 전부 **못 쓸
품질**이다. 「적당히 작은 모델로 타협」이 없다는 1절의 결론이 여기서 실전으로 확인됐다.

### 기기를 더 대 봤다 (2026-09-19) — 결론은 같다

⚠️ **「Z 폴드는 전부 스냅드래곤」이라는 통념으로 폴더블을 가져왔는데, 손에 온 것은 Z 플립이었고
플립은 엑시노스였다.** 같은 폴더블이라도 폴드와 플립이 칩을 다르게 쓴다 — 모델명으로 확인할 것
(폴드 7 = SM-F966N 스냅드래곤 / **플립 7 = SM-F766N 엑시노스 2500**).

**Galaxy Z Flip 7 (Exynos 2500, 코어 10 / 스레드 5) 실측** — `large-v3-turbo-q8_0`, NPU 켬:

```
백엔드   NEON ARM_FMA FP16_VA     ← CPU 전용. NPU 아님
스레드   5
인코더   33,961 ms  (30초 청크 1회)
디코더   9.77 ms/토큰
```

화면이 다시 같은 말을 했다: **「CPU 로 열렸습니다 — Hexagon backend not available in this build」**

28분 통화 환산: 인코더 34초 × 57청크 ≈ **32분** + 디코더 약 1분 → **33분 이상.**

| 기기 | 칩 | 28분 통화 |
|---|---|---|
| 갤럭시 S21 | Exynos 2100 | 약 3시간 |
| **갤럭시 Z Flip 7** | **Exynos 2500** | **약 33분** |
| (참고) S25 Ultra 벤치 | 스냅드래곤 + **NPU** | 2~5분 추정 |
| (기준) 서버 알리바바 | — | **1분 38초** |

🔴 **4세대를 건너뛰고 코어가 8→10, 스레드가 4→5로 늘어도 5배 빨라지는 데 그쳤다.**
34초를 3.4초로 만들려면 CPU 가 10배 빨라져야 하는데 그건 몇 세대 뒤의 일이다.
**엑시노스 계열은 세대를 올려 해결되지 않는다 — NPU 가 있느냐 없느냐의 문제다.**

## 9. 서버에서 직접 돌리면? (2026-09-19 조사) — **그것도 아니다**

폰이 막혔으니 서버 자체 호스팅을 봤다. 결론은 **Cloud Run 자체 호스팅은 답이 아니고, 옮긴다면
자체 호스팅이 아니라 더 싼 API 로 옮기는 것**이다.

환율 1 USD ≈ 1,380원, 오디오 1,706초 기준.

| 구성 | 건당 | 월 300건 | 판정 |
|---|---|---|---|
| **현행 알리바바 ASR** | **90원** | 24,810원 | 기준 |
| Cloud Run CPU 8vCPU (실측 3.7배속) | 약 180원 | 54,000원 | ❌ |
| Cloud Run CPU — 본전 배속 | 7.4배 필요 | — | ❌ 실측의 2배 |
| Cloud Run **서비스** + L4 | 43~111원 **+유휴 289원** | — | ❌ 구조적 실격 |
| Cloud Run **Jobs** + L4 (싱가포르) | 43~111원 | 12,900~33,300원 | ⚠️ 애매 |
| Batch/GCE **Spot** g2-standard-4 (서울 L4) | 28.5원 | 8,550원 | ⚠️ 운영 부담 |
| **Groq `whisper-large-v3-turbo`** | **26원** | **7,860원** | ✅ |

🔴 **결정적 사실 셋:**

1. **Cloud Run GPU 는 서울(asia-northeast3)에 없다.** 싱가포르·뭄바이·델리·유럽·미국뿐이다.
   「서울에서 GPU 를 싸게 쓴다」는 시나리오가 이 한 줄로 사라진다.
2. **CPU 전용은 손익분기가 7.4배속인데 실측이 3.7배속이다**(맥북 M2 Pro, GPU 끄고 8스레드,
   120초 오디오 → 32.4초). x86 8 vCPU 가 이보다 두 배 빠를 근거가 없다.
3. ⚠️ **GPU 를 Cloud Run 「서비스」로 붙이면 요금이 추론보다 유휴에서 더 나간다.** GPU 는
   인스턴스 기반 과금이 강제되는데 요청 후 **최대 10분 유휴 유지**라 건당 289원이 그냥 나간다.
   쓴다면 반드시 **Jobs**(태스크 종료 시 인스턴스 종료, 최소 1분 과금)여야 한다.

**그리고 직접 GPU 를 굴려도(28.5원) 같은 모델을 파는 Groq(26원)보다 싸지 않다.** Spot 선점
처리·VM 수명 관리·GPU 재고 실패 대응을 떠안고 얻는 것이 마이너스다.

### Groq — 다음에 확인할 것

`whisper-large-v3-turbo`, **$0.04 / 오디오 1시간**, 216배속(28분 통화를 약 8초).
**우리가 맥북에서 알리바바와 대등함을 확인한 바로 그 모델**이다.

⚠️ 남은 확인 둘:
1. **한국어 품질** — Groq 문서의 공식 지원 언어 목록에 한국어가 명시돼 있지 않다. 가중치가
   같아도 서버 측 전처리·VAD·청킹이 우리 whisper.cpp 설정과 다르다. **같은 통화를 넣어
   맥북 f16 결과와 CER 을 비교하면 끝난다.**
2. **화자 분리 없음** — 다만 `asr-comparison.md` 에서 **화자 표시 없이도 LLM 이 대화 흐름으로
   상담원과 고객을 갈라 요약했다.** 「타협 불가」로 잡았던 전제가 이미 약해져 있다.
3. ⚠️ 개인정보 국외 이전은 현행 알리바바와 같은 성격이나 **관할이 바뀐다.** 검토 필요.

제약: 최소 과금 10초, 파일 25MB(무료)/100MB(dev), 다중 트랙은 첫 트랙만.

### 확인 불가

- L4 GPU 에서 whisper.cpp large-v3-turbo 의 공개 실측 — 없음
- Cloud Run GPU 컨테이너의 실제 콜드 스타트 총시간(문서상 「GPU 준비 약 5초」만 확인)
- Cloud Run Jobs 표의 싱가포르 GPU 단가(페이지 갱신 실패, 서비스 표 값으로 대체 추정)
- Groq 의 한국어 전화 통화 CER

### 이어하기 검증 — 조각 단위로 재개된다

받아쓰기 도중 **20분 지점(조각 10)에서 멈췄다가** 이어하기를 눌러 **조각 11부터** 재개되는 것을
실기기에서 확인했다. **처음부터 다시 돌지 않는다.**

### ⚠️ 한계 — iOS 는 백그라운드에서 계속 돌지 않는다

- **화면을 벗어나면 받아쓰기가 멈춘다.** 안드로이드처럼 뒤에서 계속 돌려 둘 수 없다.
  그래서 이어하기는 **편의 기능이 아니라 필수**다.
- **전화가 오면 같은 이유로 끊긴다.** 끝난 조각은 남아 있으므로 통화를 마친 뒤 이어하면 된다.

7분 18초 동안 화면을 켜 두고 기다려야 한다는 뜻이다. 이 제약은 코드로 우회한 것이 아니라
**이어하기로 견디는 것**이다.

### 🔴 8절의 무엇이 뒤집혔나

**1. 「온디바이스는 실패다」라는 제목이 틀렸다.**
실패한 것은 온디바이스 자체가 아니라 **엑시노스/미디어텍 CPU 폴백**이었다. **NPU 가 있는
기기에서는 실패가 아니다.** 8절 본문의 측정과 해석(「NPU 가 있느냐 없느냐의 문제다」)은
그대로 맞았고, 그 범위를 「온디바이스 전체」로 넓혀 적은 제목이 어긋났다.

**2. 「확인에는 쓸 수 있어도 제품 경로는 아니다」의 전제 둘이 다 무너졌다.**

| 8절이 적은 전제 | 실제 |
|---|---|
| ① 받아쓰기는 **녹음이 있는 기기**에서 해야 하는데 통화를 녹음하는 것은 안드로이드다 | **앱은 녹음하지 않는다.** 파일을 올리거나 공유받아 등록하므로 **어느 기기에서 녹음됐는지는 흐름과 무관하다** |
| ② 이 앱은 **문자 발송 때문에 안드로이드 전용**이다 | iOS 는 `MFMessageComposeViewController`(시스템 시트)로 **한 건씩 보내는 경로**를 만들어 해결했다 |

⚠️ ②는 완전히 같아진 것이 아니다. **iOS 에서는 프로그램이 자동으로 발송하지 못한다** — 시스템
시트가 떠서 사용자가 보낸다. 다만 **일괄 흐름 안에서 발송/통과/중단을 고를 수 있어** 흐름이
끊기지는 않는다.

**3. 그래서 iOS 네이티브 앱을 실제로 만들어 넣었다.**
로컬 받아쓰기는 이제 두 갈래다:

| 경로 | 가속 | 상태 |
|---|---|---|
| **아이폰** | Metal | ✅ **실측 확인**(A17 Pro, 7분 18초) |
| **스냅드래곤 안드로이드** | Hexagon | ⚠️ **미검증** — 기기가 없다 |
| 엑시노스 / 미디어텍 안드로이드 | (CPU 폴백) | ❌ 불가. **앱이 그렇게 표시한다** |
