# 통화분석 — 서버 처리

앱이 하는 일은 셋뿐이다. **파일을 올리고, 상태를 묻고, 결과를 보여 준다.** 전사(STT)와 분석(LLM)은 서버 파이프라인이 한다(§`jayeon-was/internal/calls`).

이전 버전은 기기에서 whisper.rn + llama.rn 으로 직접 돌렸다. 그 코드는 이 릴리스에서 걷었다(`git show HEAD:src/lib/call-runtime.ts` 로 볼 수 있다). 무엇을 왜 남겼는지는 아래 「구버전에서 넘어온 것」에 적는다.

## 흐름

```
① POST /calls/{call_id}/audio/upload-url   서명 URL 발급 + 통화 메타 등록
② PUT  <서명 URL>                          앱 → GCS 직접. 서버를 거치지 않는다
③ POST /calls/{call_id}/audio/complete     객체 확인 후 큐잉(응답 = CallSummary)
④ GET  /calls/{call_id}                    진행 중일 때 5초 간격 폴링
⑤ POST /calls/{call_id}/reanalyze          전사문 재사용, LLM 만 다시
```

`call_id` 는 **앱이 만든다**(UUID). 서버의 객체 경로가 이 ID 로 정해지므로(`calls/{uid}/{call_id}/audio.m4a`) **재시도는 반드시 같은 ID 로 한다** — 새 ID 를 뽑으면 못 쓰는 객체가 버킷 보관 기간(366일) 내내 남는다. 이 규칙은 `lib/call-upload.ts` 가 지키고, 실패한 시도의 ID 는 `CallUploadError.callId` 로 돌아온다.

🔴 **응답의 `headers` 를 글자 그대로 PUT 에 실어야 한다.** `Content-Type` 이 서명에 들어가므로 한 글자만 달라도 GCS 가 403 `SignatureDoesNotMatch` 를 주는데, 응답만 봐서는 원인을 알 수 없다. 그래서 앱은 자기가 만든 MIME 이 아니라 **서버가 돌려준 값**을 싣는다(단위 테스트가 이것을 확인한다).

③ 은 **이미 큐잉된 통화에 다시 불러도 200** 이다. 그래서 `complete` 응답을 받지 못했을 때 앱은 마음 놓고 다시 부를 수 있고, ① 이 409 `CALL_ALREADY_QUEUED` 로 막히면 업로드를 건너뛰고 ③ 만 부른다.

## 업로드 구현 — 웹이 직접 올린다

이 앱은 인증까지만 네이티브가 그리고 그 뒤 화면은 껍데기의 웹뷰가 연다(→ `components/web-shell.tsx`). 그래서 통화분석 화면은 **브라우저에서도 껍데기 안에서도 같은 웹 코드**다.

- **웹**(`lib/call-put.web.ts`): `<input type="file">` 로 고른 `File` 을 `XMLHttpRequest` 바디로 **그대로** 보낸다. 진행률은 `xhr.upload.onprogress`, 취소는 `xhr.abort()`.
  - 🔴 **base64 로 바꾸지 않는다.** 28MB 파일이 문자열로 38MB 가 되고 원본까지 함께 메모리에 올라간다 — 폰 웹뷰가 그 자리에서 죽는다.
  - 🔴 `fetch` 가 아니라 XHR 인 이유는 업로드 진행률 하나다. `fetch` 는 요청 바디가 얼마나 나갔는지 알려 주지 않는다.
  - 껍데기 안에서도 안드로이드 웹뷰가 기본 파일 선택기를 띄운다(`allowFileAccess`). **브리지로 파일 바이트를 나르지 않는다** — 껍데기 메시지는 64KB 에서 끊긴다.
- **네이티브**(`lib/call-put.ts`): `expo-document-picker` 로 고르고 `expo-file-system` 의 업로드 태스크(`BINARY_CONTENT`)로 디스크에서 스트리밍한다. 진행률은 `totalBytesSent`, 취소는 `cancelAsync()`. 네이티브로 직접 연 화면(개발 빌드)을 위한 길이다.

두 전송기는 같은 타입(`lib/call-put-types.ts`)을 구현하고, 실패는 **코드 문자열 하나**로만 거절한다(`UPLOAD_CANCELED`·`UPLOAD_NETWORK`·`HTTP_403` …). 저장소 응답 본문에는 서명 정보가 섞여 있어 그대로 내보내면 안 된다.

파일 선택 버튼은 **감춘 `<input type="file">` 을 덮은 우리 버튼**이다(`components/call-file-field.web.tsx`). 브라우저 기본 컨트롤(「파일 선택 | 선택된 파일 없음」)은 같은 시트의 다른 버튼과 크기도 모양도 맞지 않고, 파일을 고른 뒤에도 아래 줄과 다른 말을 한다. 입력은 `display:none` 이 아니라 **투명하게 덮는다** — 감추면 키보드 초점이 닿지 않아 키보드만으로 파일을 열 수 없다. 고른 뒤에는 버튼 아래에 `이름 · 크기` 한 줄을 세우고, 다시 고르려면 같은 버튼을 누른다. 네이티브 경로도 같은 모양(`SmsButton` secondary)이다.

파일 형식은 **확장자로 정한다**(`lib/call-file.ts`). 같은 m4a 를 두고 크롬은 `audio/x-m4a`, 사파리는 빈 문자열을 주는데 둘 다 서버 화이트리스트에 없다. 확장자를 모를 때만 브라우저 값을 본다. 크기(1~100MiB)·연락처·통화일시는 **요청을 보내기 전에** 거른다 — 28MB 를 올린 뒤 400 을 받는 것이 가장 나쁘다.

## 진행 표시

화면의 네 단계는 **업로드 → 음성 변환 → 분석 → 완료**다(`lib/call-progress.ts`). 서버 status 를 이 넷으로 묶는다.

| status | 서버 job_state | 단계 |
| --- | --- | --- |
| `PENDING` / `UPLOADING` | `AWAITING_UPLOAD` | 업로드 |
| `PREPARING` | `QUEUED` | 음성 변환(순서 대기) |
| `TRANSCRIBING` | `ASR_RUNNING` · `ASR_POLLING` | 음성 변환 |
| `ANALYZING` | `TRANSCRIBED` · `ANALYZING` | 분석 |
| `COMPLETED` | `COMPLETED` | 완료 |
| `TRANSCRIPTION_FAILED` / `ANALYSIS_FAILED` | 같음 | 멈춘 자리 |

🔴 **`progress` 는 0~1 실수다.** 기기 분석 시절에는 0~100 정수였다 — 두 뜻이 한 필드에 섞이면 막대가 1% 에서 멈춘 것처럼 보인다. 앱 안에서도 언제나 0~1 로 다루고 그릴 때만 백분율로 바꾼다(`percentOf`). 범위 밖 값은 **버린다**(막대를 그리지 않는다) — 옛 값이 섞여 들어오면 여기서 걸린다.

🔴 **가짜 진행률을 만들지 않는다.** 막대에 들어가는 값은 둘 중 하나다.

- **업로드 단계**: 앱이 실제로 보낸 바이트(`업로드 N%`).
- **서버 단계**: 서버가 보낸 전체 진행률(`전체 진행률 N%`). 단계별 고정값이라(§`job.go` 의 `progressOf`) 「멈춰 있지 않다」는 뜻이지 그 단계의 완료율이 아니다 — 그래서 **이름을 다르게 적는다.**

지금 무슨 일이 벌어지는지는 서버가 준 `stage` 한 줄을 그대로 쓴다(「받아쓰는 중」). 앱이 지어내지 않고, 값이 없는 옛 기록에서만 앱의 단계 이름으로 대신한다. 서버는 단계별 소요 시간을 주지 않으므로 **지나간 단계에 시간을 적지 않는다** — 진행 중인 단계에만 `created_at` 기준 경과 시간을 붙인다.

폴링은 **진행 중인 통화가 있을 때만** 돈다. 5초 간격으로 **상세**(`GET /calls/{id}`)를 최대 5건까지 묻는다. 목록을 다시 받으면 30건을 통째로 받고도 `stage` 말고는 새로 알 것이 없고, 상세 조회는 서명 URL 발급 + 작업 문서 읽기라 목록보다 비싸다. 2초는 같은 답을 스무 번 더 받는 일이라 쓰지 않는다.

## 목록과 검색

**거르기는 서버가 한다.** `GET /calls?q=&limit=&cursor=` 이고, `q` 의 매칭 규칙(하이픈·공백·`+82` 흡수, 숫자만 비교, 글자+숫자 혼합)은 앱의 `lib/recipient-search.ts` 와 같은 규칙을 서버가 그대로 구현했다. 🔴 **앱에서 한 번 더 거르지 않는다** — 규칙이 한 글자라도 어긋나는 순간 서버가 찾아 준 통화를 앱이 조용히 떨어뜨리고, 아무도 눈치채지 못한다.

- `limit` 은 50 으로 보낸다(서버 상한 100). 예전에는 30건 고정이라 한 화면을 채우려고 두 번씩 불렀다.
- 입력은 **300ms 디바운스**한다. 한 글자마다 부르면 「홍길동」을 치는 동안 서버가 문서를 여섯 번 훑는다.
- 🔴 **`q` 가 바뀌면 커서를 버린다.** 커서 안에 그 검색어가 들어 있어(§`store.go` 의 `cursorData.Q`) 다른 검색어의 커서를 보내면 400 이다.
- 🔴 **`items` 가 비어도 끝이 아니다.** 끝인지 말하는 것은 `nextCursor` 하나뿐이다. 검색은 최신순으로 문서를 훑어 메모리에서 거르는데 한 번에 훑는 수(300)에 상한이 있어, **0건 + 커서**가 정상 응답이다. 그대로 그리면 「결과 없음」이 뜨고 목록이 짧아 스크롤도 안 생기므로 다음 요청이 영영 나가지 않는다 — `callApi.batch` 가 뭔가 찾거나 커서가 없어질 때까지 이어 부른다(최대 6회. 없는 이름 하나로 컬렉션 전체를 훑지 않기 위해서다).
- 그래서 「해당하는 통화가 없습니다」는 **커서가 없을 때만** 띄운다. 커서가 남아 있으면 「여기까지는 찾지 못했습니다. 아래로 내리면 이어서 찾습니다」로 적는다.
- 「불러온 N건 안에서 찾았습니다」 같은 한계 안내는 없앴다 — 이제 서버가 전체에서 찾는다.
- 늦게 도착한 응답이 지난 검색 결과를 그리지 않도록, 화면은 **지금 보여 주는 검색어**(`showing`)와 다른 응답을 버린다.

발송 이력 검색(`GET /sms/history?q=`)도 같은 규칙으로 전화번호를 찾는다. 앱 쪽 변경은 없다(검색칸 문구가 이미 「이름,전화번호 뒷자리 4자」다).

## 재시도

- **분석이 실패한 통화**(`ANALYSIS_FAILED`)에만 「분석 다시 시도」가 선다 → `POST /reanalyze`. 오디오를 다시 전사하지 않고 저장된 원문으로 LLM 만 다시 돌린다. ASR 이 가장 비싼 단계이고, 재분석이 필요한 이유는 대개 분석 쪽에서 났다.
- **받아쓰기가 실패한 통화**(`TRANSCRIPTION_FAILED`)에는 다시 분석할 원문이 없어 서버가 409 `CALL_NO_TRANSCRIPT` 로 거절한다. 그래서 버튼을 세우지 않고 「다른 녹음 파일로 다시 등록해 주세요」라고 적는다 — 누를 수 있는 버튼을 세워 두고 거절당하게 하지 않는다.
- **업로드 실패**는 등록 시트에서 그 자리에 코드와 이유가 남고, 같은 ID 로 다시 시도한다. 4xx(401·403·408·429 제외)는 영구 실패로 보고 5xx·연결 실패는 재시도 대상이다(`permanentFailure`).

실패 이유는 **정해진 코드로만** 남긴다(`lib/call-errors.ts`). 서버의 `error` 는 문장이 아니라 코드이고(`EMPTY_TRANSCRIPT`, `CONTENT_FILTERED`, 공급자 코드 `Throttling.RateQuota` …) 우리가 뜻을 모르는 값이 정상적으로 들어온다. 그때는 아는 척하지 않고 「알 수 없는 오류입니다. (코드: X)」로 적는다 — **코드를 지우면 다음에도 추측밖에 할 수 없다.**

## 녹음 재생

- 목록(`GET /calls`)에는 **`audio_url` 이 오지 않는다.** 30건마다 서명 30개를 만들지 않기로 했기 때문이다. 목록이 받는 것은 `has_audio` 하나이고, 그것이 ▶ 를 열지 정하는 유일한 근거다.
- 주소는 상세를 조회할 때 **15분짜리 서명 GET URL** 로 새로 발급된다. 재생 패널이 열릴 때 상세를 한 번 물어본다(→ `components/call-playback.tsx`).
- 들을 수 없으면 **이유를 말한다**: 기기에서 분석한 옛 통화(서버에 원본이 없다) / 보관 기간(366일) 경과 / 아직 준비 안 됨. 소리 나지 않는 재생기를 그려 두면 사용자는 자기 기기를 의심한다.

## 구버전에서 넘어온 것

**서버의 기기 업로드 경로(`PUT /calls/{id}`)는 그대로 살아 있다.** 그 경로로 저장된 옛 통화에는 `job_state`·`stage`·`has_audio`·`audio_url` 이 없다. 화면은 그 값들을 모두 선택적으로 읽고, 없으면 앱의 단계 이름과 「서버에 원본 녹음이 없습니다」로 대신한다.

기기 분석 버전이 **분석까지 끝내 놓고 서버 저장에 실패한 통화**가 사용자 기기에 남아 있다. 그대로 두면 앱을 업데이트하는 순간 사라진다. `lib/call-runtime.ts` 를 큐·백오프 뼈대만 남겨 **조용히 마저 올리는 작업자**로 다시 썼다(네이티브 껍데기 전용, 화면 없음). 성공한 결과는 서버 목록을 통해 사용자에게 돌아온다.

- 로컬 SQLite 는 이름을 **바꾸지 않는다**(`nature-calls-v1.db`). 이름을 바꾸면 새 빈 DB 가 생기고 옛 파일은 아무도 열지 않는 채 남는다.
- 새로 쓰는 표는 `calls` 와 `sync_status` 둘뿐이다. `transcripts`·`call_analyses` 는 **읽기만** 하고(못 올린 결과를 꺼내려고), `analysis_chunks` 는 건드리지 않는다.
- **TODO(별도 릴리스): 모델 파일 787MB 와 남은 옛 표를 지운다.** 이번에 지우지 않는 이유는 롤백이다 — 지우면 되돌렸을 때 787MB 를 다시 받아야 한다.
- `modules/nature-call-audio` 는 **`excludeFromBackup` 하나만 남긴 축소판**이다. `decode`(MediaCodec/AVAssetReader → 16kHz WAV)·`sha256`(모델 검증)·`cpuCount`(추론 스레드)는 부르는 곳이 없어졌다. 백업 제외는 아직 필요하다 — 위의 「아직 못 올린 통화 원문」이 iOS 에서 iCloud 백업에 올라가면 통화 내용이 사용자의 백업에 그대로 복사된다. Android 는 `allowBackup:false` 라 no-op 이다.
- 걷은 것: `llama.rn`·`whisper.rn`·`buffer` 의존성, `plugins/with-call-ai.cjs`(+ `app.json` plugins), `lib/call-models.ts`, `lib/call-threads.ts`, `lib/call-device.ts`/`.web.ts`, `lib/call-shell-handler.ts`, 껍데기의 `call` 브리지, `scripts/call-analysis-estimate.cjs`. `lib/call-analysis.ts` 에는 업로드 직전 원문 정리(`sanitizeTranscript`)만 남았다.

## 개인정보

원본 녹음은 GCS 로 올라가 약 366일 보관된 뒤 버킷 수명주기 정책으로 삭제된다. 전사문과 분석은 Firestore 에 남는다(원본이 사라져도 남는다). 오디오 바이트는 **서버를 통과하지 않는다** — 앱이 서명 URL 로 GCS 에 직접 올린다.

🔧 **화면에는 이 사실을 알리는 고지 문구가 없다**(사용자 결정, 2026-09-18). 목록 상단과 등록 시트에 한 줄씩 두었다가 둘 다 걷었다. 어디에 어떻게 고지할지는 **약관·개인정보 처리방침 쪽에서 따로 정한다** — 이 문서는 그때 참고하도록 「지금은 화면에 없다」는 사실만 기록해 둔다.

실패 문구·로그에 통화 원문이나 네이티브 예외 원문을 넣지 않는다(`lib/call-errors.ts` 의 코드 화이트리스트). 저장소 응답 본문도 상태 코드만 남긴다.

## 검증

- `npx tsc --noEmit`, `npx expo lint`, `npm run test:calls`, `npm run test:auth`, `npm run test:sms`.
- `npm run test:calls` 가 보는 것: 업로드 3걸음의 **순서와 횟수**, 서버가 준 헤더를 그대로 싣는지, `duration` 을 지어내지 않는지, 진행률 콜백, 취소(큐잉까지 가지 않는다), 409 재호출 안전, 실패 분류(4xx 영구 / 5xx·연결 재시도), 요청 전 검증(연락처·통화일시·크기), 확장자 기준 MIME 판정, 0~1 진행률과 범위 밖 값 버리기, 네 단계 사상, 서버 `stage` 우선, 경과 시간(끝난 통화에는 붙이지 않는다), `has_audio` 기준 재생 판정, 실패 코드 화이트리스트, 업로드 전 원문 정리.
- `npx playwright test tests/e2e/calls.spec.ts` 가 보는 것: 파일 선택 → 등록(upload-url → PUT → complete 순서와 `Content-Type`) → 업로드 막대·취소 → 5초 폴링으로 단계 갱신 → 완료 뒤 폴링 정지, 실패 코드 표시와 `reanalyze` 호출, 받아쓰기 실패의 안내, 원본 없는 통화의 잠긴 ▶, `limit=50` 한 번에 받기와 무한 스크롤, 검색어를 서버로 보내고 **앱이 다시 거르지 않는 것**, 디바운스(네 글자에 요청 한 번), `q` 가 바뀔 때 커서를 버리는 것, **0건 + 커서 응답에도 스스로 이어 부르는 것**, 정말 없을 때만 「없습니다」를 띄우는 것.
- 알려진 무관 실패 2건(`sms.spec.ts` 의 「이미지 템플릿…」)은 이 작업과 상관없이 그대로다.

### 서버 배포 전이라 확인하지 못한 것

모의(mock)로만 검증했다. 아래는 **실서버·실기기에서만 드러난다.**

- **GCS CORS.** 브라우저(그리고 웹뷰)에서 서명 URL 로 직접 PUT 하려면 버킷 CORS 가 그 오리진의 `PUT` 과 `Content-Type` 헤더를 허용해야 한다. 안 되어 있으면 **서버 로그에는 아무것도 남지 않고** 브라우저 콘솔의 CORS 오류로만 보인다.
- 서명 URL 의 실제 `Content-Type` 일치(403 `SignatureDoesNotMatch` 여부), 만료(60분) 안에 느린 회선이 100MB 를 올리는지.
- 실제 전사·분석 소요 시간과 그동안의 `stage` 문구 변화, 5초 폴링 간격의 체감.
- 안드로이드 웹뷰의 파일 선택기에서 실제 통화 녹음(`.m4a`/`.3gp`)이 목록에 보이는지, `lastModified` 가 원본 시각으로 오는지.
- 큰 파일(수십 MB) 업로드 중 화면 전환·백그라운드 전환에서 XHR 이 끊기는지.
- 옛 기기 기록의 마저 올리기(`PUT /calls/{id}`)가 실제 계정에서 200 을 받는지.
